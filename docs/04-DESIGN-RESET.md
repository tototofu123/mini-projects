# Design Reset — From Portfolio Template to Constraint Ledger

## What failed

The current normal portfolio is polished, but it reads as an assembled portfolio template instead of a site that could only belong to Toto. Its familiar ingredients are a left rail, an oversized serif hero, a card grid, colour-coded abstract diagrams, an editorial lifestyle image, and a dark concluding section. None of those elements are wrong individually; together they make the work feel like a generic AI art direction.

The most serious issue is that the visual material is **not evidence**. The trace diagrams do not come from a real OCR route, STM32 signal path, CNN pipeline, or Perihel flow. They are decorative stand-ins. That weakens the exact thing the portfolio needs to prove: that Toto builds actual systems.

## What is specific to Toto

The selected work is not tied together by one aesthetic. It is tied together by a repeated working pattern: **a messy constraint appears, and Toto turns it into a system with a usable interface**.

| Constraint | System response | Project |
|---|---|---|
| A community has different member, organiser, and information needs | A joined-up full-stack product | HKUST Climbing App |
| OCR output varies by document and model | A local comparison and routing workflow | OCR MCP |
| A physical device has to behave predictably | Firmware and hardware that meet at a real interface | STM32 |
| An image classifier can be confidently wrong | A CNN experiment with visible limits | Is It AI Image? |
| A community needs an understandable public face | A responsive content interface | HKUST Climb Society Web |
| Small intentions disappear before they become action | A local-first capture and return loop | Perihel |

## New direction: Constraint Ledger

The normal portfolio becomes a **ledger of six constraints**, not a gallery of projects. A visitor enters through a blunt premise:

> “I build when something needs to hold together.”

Each project appears as a large case entry with this deliberate order:

```text
THE CONSTRAINT
What was difficult or uncertain?

THE RESPONSE
What system did I build?

THE PROOF
What actual artifact can a visitor inspect?

THE LIMIT
What remains incomplete or needs care?
```

There is no hero stock image, no project-card grid, no fake technical circuitry, no faux dashboard, and no dark/light “portfolio section” formula. Typography is utilitarian and direct. The experience feels closer to a field report, technical incident ledger, or engineering change log—but the content is personal and readable.

## Visual rules

The site uses one high-contrast ink colour, one bright operational blue, and one paper surface. Every line, glyph, route, or diagram must come from a real project relationship. When a project has no real visual yet, the site shows text and a structured evidence placeholder instead of decorative imagery.

The layout should alternate between broad, almost poster-like problem statements and dense case annotations. Case entries are not equal cards: the full-stack app and OCR tool can receive more visual weight because they carry more available system detail. Perihel can be small, intimate, and text-first.

## Direction to validate

Before replacing the current interface, validate this sentence:

> **The normal portfolio is a ledger of six real constraints and the systems Toto built in response.**

If that feels right, the redesign will be structurally different rather than a reskin.
