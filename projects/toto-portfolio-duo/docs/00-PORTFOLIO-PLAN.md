# Portfolio Duo — Product Plan

## The decision

Build **two portfolio copies from one canonical project dataset**. The normal portfolio is the default link shared with recruiters. The showcase is a second link for people who want a more memorable, exploratory view of the work. This avoids the usual compromise where a single portfolio is either too safe to remember or too theatrical to scan.

> The normal version is responsible for trust. The showcase version is responsible for recall.

## Audience and conversion path

| Audience | Normal portfolio need | Showcase portfolio need | Desired next step |
|---|---|---|---|
| Hiring manager | Scope, role, outcomes, and readable proof in under three minutes | Optional signal of taste and craft | Open a case study or contact Toto |
| Engineer | Stack, architecture, trade-offs, repository links, and limits | A close-up of systems thinking | Inspect implementation evidence |
| Product or design collaborator | User problem, interaction choices, and visual clarity | Sense of curiosity and product judgement | Start a collaboration conversation |

## Shared positioning

**Toto Lai builds useful software systems across full-stack web, embedded C, Python AI tooling, and applied machine learning.** The portfolio should make climbing only one source of real product context—not Toto’s identity.

## The six-project editorial order

The project order should communicate breadth without feeling random. Lead with one complete software product, then alternate between technical domains.

| Order | Project | Why it appears here |
|---:|---|---|
| 01 | HKUST Climbing App | Strongest full-stack, user-facing product anchor |
| 02 | OCR MCP | Current AI tooling and Python orchestration |
| 03 | STM32 | Hardware and C create a clear technical contrast |
| 04 | Is It AI Image | Computer vision and ML experimentation |
| 05 | HKUST Climb Society Web | Frontend delivery for a real community context |
| 06 | Perihel | Personal product thinking, ideas, and reminder workflow |

## Non-negotiable rules

The portfolio must not claim metrics, users, production reliability, or technical features without evidence. Every project needs an explicit **what I built**, **what was difficult**, **what I would improve**, and **evidence** block. The website must be usable without animation, work from a keyboard, preserve readable contrast, and never require a visitor to understand climbing in order to understand Toto’s work.

## Build sequence

| Step | Output | Stop condition |
|---:|---|---|
| 1 | Canonical six-project records | Each has facts, links, role, media, and limitations |
| 2 | Normal portfolio | A recruiter can understand Toto and the six projects without motion or scrolling tricks |
| 3 | Showcase portfolio | Each interaction directly explains a real technical idea or product decision |
| 4 | Evidence pass | Links, screenshots, code claims, and accessibility checks are verified |
| 5 | Deploy decision | Select a primary portfolio URL and an optional showcase URL |
